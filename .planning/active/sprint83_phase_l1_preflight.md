## S1a Prior-art OSS

**Coffres de secrets Rust — état de l'art.** La voie canonique est `keyring` (open-source-cooperative/keyring-rs) : `Entry::new(service, account)` + `set_secret`/`get_secret`/`delete_credential`, backends natifs Windows Credential Manager, macOS Keychain, Linux Secret Service, toujours synchrone, zeroize côté appelant ([docs.rs/keyring](https://docs.rs/keyring/latest/keyring/index.html)). Modèle secret-handle-opaque : n8n stocke les credentials comme entités chiffrées séparées, le workflow JSON ne portant QUE des IDs résolus à l'exécution ([n8n Credentials/Security, DeepWiki](https://deepwiki.com/n8n-io/n8n/3.2-credentials-api-and-security)) ; HashiCorp Vault retourne des secrets dynamiques JIT (`lease_id`/TTL), « applications never handle long-lived secrets directly » ([Vault static vs dynamic](https://developer.hashicorp.com/vault/tutorials/get-started/understand-static-dynamic-secrets)). HITL autoritaire = WebAuthn Transaction Confirmation / FIDO TxConf (WYSIWYS « What You See Is What You Sign », `challenge` anti-replay, seul le composant d'affichage doit être de confiance) ([w3c webauthn-pay TxConf](https://github.com/w3c/webauthn-pay/blob/gh-pages/proposals/pr-webauthn-txconf.md), [webauthn.guide](https://webauthn.guide/)).

**Ce que le repo fait DÉJÀ (mesuré).** Le keystore est de qualité production et porte tout le pattern coffre : double-wrap Argon2id(PIN)+kek2, AES-256-GCM, AAD `DOMAIN_KEYSTORE_V1`+header anti-downgrade, `SecretBox`+`zeroize` partout, `write_atomic` 0600, rotation (`rotate_pin` `keystore.rs:679`), suppression zero-overwrite (`wipe`/`wipe_all` `:769`/`:995`, `secure_unlink_blob` `:1017`), duress, trait `KeyStore` (`:400`). La discipline opacité est déjà enforced statiquement dans le core pur : `crates/sbfb-workflow-core/src/pack.rs:421-428` (`secret_refs: Vec<String>` = « names a slot, never a secret »), refus d'un secret matérialisé `pack.rs:918-924` + `looks_like_materialised_secret` (`compile.rs:755`), la valeur refusée retirée des messages d'erreur. La classe `CapabilityClass::SecretUse` (`capability.rs:171-173`) est typée « bound just-in-time by the host keystore ». Le layer 7 HITL est déjà modélisé dans l'algèbre pure — `HitlValidity { decided_refs }` (`capability.rs:586-596`), VIDE en L, fail-closed sur `ApprovalLevel::Human` (`:221`), invariant `hitl_gate_must_run_after_approval_raise` (`:638-647`), doc annonçant « Secret binding and the signed HITL principal are Phase L1 » (`:110-111`). L'anti-replay HITL est LIVE depuis Phase K : `T-RUN-SIGNAL-FORGE-REPLAY` (`THREAT_MODEL.md:1811`) — nonce engine-dérivé, `INSERT OR IGNORE` mono-usage, consommation CAS atomique, expiration vs `now_ms`.

**Delta L1.** Coffre = généralisation du keystore mono-identité vers un coffre nommé indexé par `secret_ref` opaque (bind JIT / rotate / delete / zeroize / audit) ; seam moteur `secret` (comme `clock.rs`/`signal.rs`) — le moteur ne connaît QUE la ref opaque, l'hôte résout ; binding JIT dans l'adaptateur d'effet Phase K juste avant l'appel (`EffectContext.input` = `{port → JCS}` seulement, `activity.rs:68`) ; HITL = rendu chrome hôte lié au digest exact du tuple + liaison autoritaire hôte + file persistante + a11y. Le delta HITL est plus étroit que la prose L1.2 ne le suggère : nonce/seq/expiration/mono-usage sont déjà faits (Phase K).

### P2 (à fermer avant PASS, non-bloquants pour le commit)

**F1 — P2 — `capability.rs:568-570` — l'invariant « l'ordre des couches n'affecte pas le résultat » est FAUX pour la couche 7 (HITL) et son placement porteur n'est épinglé par AUCUN test.**
Le docstring de `effective_capabilities` affirme « Layer application order does not affect the result (meet is commutative and associative) ». Or la couche 7 (`:610-611`) filtre sur `cap.approval`, champ que les meets des couches 2/3/4 ÉLÈVENT par `.max` (`BoundedCapability::meet:324`, `meet_with_allow`, `meet_with_grants`). Contre-exemple discriminant : `declared["x"].approval = Auto`, un grant conférant `["x"]` avec `approval = Human`, `HitlValidity::none()`. Ordre réel (HITL dernier) → meet monte à `Human` → couche 7 DROP (correct). Ordre inversé → couche 7 voit `Auto`, garde → grant monte à `Human` → survit **sans décision = fail-open HITL**. `human_approval_requires_valid_decision:1225` utilise un grant `top(Push)` (approval `Auto`, incapable d'élever) ; `intersection_only_attenuates` ne l'attrape pas (le ref survivant reste membre de `declared`, `refines` tient). Une mutation « HITL avant les grants » reste donc VERTE. *Pourquoi ça compte* : module de sécurité, invariant faux, placement load-bearing non testé, et la phase run-surface est censée bâtir directement dessus. *Correctif* : (i) réécrire le commentaire — « les couches 1-6 (meets/filtres de clés) commutent ; la couche 7 (filtre sur seuil d'approbation) DOIT rester en dernier, après tout meet élevant l'approbation, sous peine de fail-open HITL » ; (ii) ajouter un test discriminant : `declared["x"].approval=Auto` + grant release/pack `approval=Human` + `HitlValidity::none()` → `len()==0` ; même cas avec `decided_refs={"x"}` → `len()==1`.

**F2 — P2 — `capability.rs:593-595` + `:619-625` — la couche 2 (policy locale opérateur / `meet_with_allow`) n'a AUCUN test discriminant ; une mutation no-op survit aux 13 tests.**
Le seul test non-`OpenPolicy` est `os_toggle_class_filter:1344`, dont `local_policy()` renvoie `RefConstraint::Unconstrained`. La branche `RefConstraint::Only(...)` n'est exercée que dans `intersection_only_attenuates`, qui n'assère que `refines(&base)`/`refines(&declared)` — or `base = declared.filtered(closure)` **n'applique pas la couche 2**. Une mutation `meet_with_allow → eff.clone()` (ignore l'allow-map) laisse `eff` plus LÂCHE mais toujours ⊆ base ⇒ `refines(base)` tient ⇒ mutation survivante. *Pourquoi ça compte* : la couche 2 est l'autorité deny/tighten de l'opérateur ; un bypass silencieux = privesc vs intention opérateur, et la claim « les property tests prouvent l'atténuation monotone des 7 couches » n'est PAS test-appuyée pour la couche 2 (le widening est attrapé ; le no-op / la non-atténuation ne l'est pas). *Correctif* : test dédié miroir de `os_toggle_class_filter` avec une policy `RefConstraint::Only(map)` où (a) un ref absent de l'allow-map est droppé et (b) un ref présent avec une borne plus serrée (`quota=AtMost(1)`, `approval=Human`) est meet-tightened — asserter la borne EXACTE du survivant, pas seulement sa présence.

**F3 — P2 — `capability.rs:264-274` (déf. `DataPolicy`) + `:323` (`meet` prend `max`) — le treillis `DataPolicy` linéarise `max` sur des axes sémantiquement orthogonaux → relâchement de confinement de localité possible.**
Variantes `Unrestricted < LocalOnly < Ephemeral`, doc « ORDERED least-to-most restrictive », meet = `self.data_policy.max(other)`. Mais les définitions décrivent DEUX dimensions : `LocalOnly` = « data must stay within the local node » (localité/egress) ; `Ephemeral` = « never persisted beyond the effect » (persistance). `Ephemeral` n'implique PAS `LocalOnly` (une donnée éphémère peut sortir du nœud en transit sans être persistée). Donc `meet(LocalOnly, Ephemeral) = Ephemeral` PERD la contrainte de localité ; `refines` (`:336`) assère qu'`Ephemeral` refine `LocalOnly`, mensonger sous la lecture orthogonale. `approval_meets_by_max_not_min:1314` ENTÉRINE ce comportement (`assert_eq!(m.data_policy, Ephemeral)`) — délibéré, donc décision de design, pas un slip. C'est exactement le soin « direction par champ » que PA-5 a élevé pour l'approbation, non appliqué à `data_policy`. *Pourquoi ça compte* : si une couche impose `LocalOnly` (jamais d'egress) et un grant `Ephemeral`, l'intersection rend `Ephemeral` seul → un futur enforcer laisserait la donnée quitter le nœud malgré la politique de localité ; algèbre autoritaire gelée de fait. *Correctif* : soit (a) rendre l'implication EXPLICITE et la garantir — documenter/enforcer `Ephemeral ⊨ LocalOnly ⊨ Unrestricted` (chaque niveau hérite strictement du précédent) ; soit (b) modéliser `DataPolicy` en flags indépendants (`no_persist`, `no_egress`) meet par UNION. À trancher avant qu'un producteur de couches n'existe. (Note : `ApprovalLevel` `Auto<Notify<Human` est, lui, défendablement total — l'asymétrie est propre à `DataPolicy`.)

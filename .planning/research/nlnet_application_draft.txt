ABSTRACT (max 1200 characters — currently ~1100)
====================================================================

SBFB is a peer-to-peer compute network where anyone can publish and
run web applications without central servers. Apps are distributed
as signed web archives via the iroh P2P stack, rendered in sandboxed
iframes, and verified from source using Ed25519 + SLSA L1 provenance.

The project is feature-complete for a first public release (107k LOC,
~1900 tests, 32 sprints of development, AGPL-3.0) but has never been
independently audited. As a solo-maintainer open-source project with
no commercial funding, I cannot afford a professional security audit.

I am requesting NLnet support specifically for an independent security
audit covering: (1) the P2P protocol and wire format (iroh-based
gossip, docs, blobs), (2) cryptographic primitives (Ed25519, FROST
threshold signatures, Argon2id keystore, AES-256-GCM), (3) iframe
sandbox and CSP isolation for untrusted apps, (4) loopback HTTP API
authentication. All findings will be published publicly.

Expected outcome: a published audit report, remediation of critical
findings, and a v1.0 release that users can trust. The code, threat
model, and audit results will all be open.

COMPARE WITH EXISTING EFFORTS (max 4000 chars — currently ~2800)
====================================================================

SBFB occupies a unique position at the intersection of P2P compute
networks and open-source app distribution:

vs BOINC / Folding@Home / Golem:
Traditional volunteer compute projects use a central coordinator.
SBFB has no central server — each project creator runs their own
coordinator, workers choose which projects to serve via
cryptographic allowlists, and reputation propagates via Ed25519-
signed curator lists over gossip. The compute model is LLM
inference (Ollama), not batch scientific computation.

vs IPFS / libp2p:
These provide P2P content distribution but not compute. SBFB uses
iroh (a Rust P2P stack by n0, inc.) for networking and adds: task
dispatch with result verification, GPU consent, structured output
validation, and an application rendering layer via sandboxed iframes.

vs F-Droid / Flathub:
Traditional app stores require a central review process. SBFB apps
are verified from source automatically: the coordinator clones the
Git repository, verifies the developer's Ed25519 identity via
Keyoxide, builds the archive, and signs SLSA L1 provenance. Users
can fork any app and deploy their own version in one click.

vs Tauri / Electron:
Desktop app frameworks bundle a browser engine per app. SBFB uses
the user's existing browser: a Rust launcher spawns the daemon,
which serves apps in sandboxed iframes. Any web technology (React,
WASM, Pyodide, plain HTML) works without per-app packaging.

vs Fediverse (Mastodon, Matrix):
Federated systems still require server administrators. SBFB
requires zero administration — nodes self-organize via DHT
discovery (pkarr), and the only trust anchor is the developer's
Ed25519 key.

Key novelties:
- Hybrid Rust+Python architecture with JCS canonical byte-identical
  signatures across the FFI boundary
- Warrant canary with FROST threshold signatures (K-of-N across
  jurisdictions)
- Universal web archive rendering in sandboxed iframes
- Verified deploy from source with zero OAuth (multi-forge via
  Keyoxide)

TECHNICAL CHALLENGES (max 5000 chars — currently ~1600)
====================================================================

The audit needs to evaluate several non-trivial attack surfaces:

1. iframe sandbox escape: apps run with sandbox="allow-scripts"
   (no allow-same-origin) and CSP connect-src 'none'. The auditor
   must validate that no browser-specific behavior allows sandbox
   escape, host origin access, or data exfiltration. This is the
   highest-impact attack surface.

2. Wire format integrity: all signed structures use JCS (RFC 8785)
   canonical JSON with Ed25519 domain separation. The auditor must
   verify that canonicalization is correct and that no malleability
   exists in the wire format before it is frozen at v1.0.

3. Loopback API authentication: the daemon serves an HTTP API on
   localhost with bearer token + SO_PEERCRED/DACL + Host/Origin
   validation. The auditor must verify that a malicious browser
   extension or local process cannot bypass these layers.

4. Keystore security: Ed25519 private keys are encrypted with
   Argon2id (64 MiB, t=3) + AES-256-GCM, wrapped in OS keyring.
   The auditor must verify the key derivation parameters resist
   GPU brute-force and that the double-layer defense is sound.

5. FROST ceremony: warrant canaries use K-of-N threshold
   signatures. The auditor must verify the DKG implementation
   and that no single participant can forge a signature.

under a Creative Commons license. The threat model (already public)
and the audit report together will serve as reference documentation
for other P2P projects facing similar security challenges.

Target users: independent journalists, NGOs needing censorship-
resistant publishing, open-source developers wanting to distribute
apps without platform gatekeepers, privacy-conscious contributors.

no commercial ambition. The network is self-sustaining by design
(no servers beyond bootstrap peers). This grant does not create
funding dependency — it provides a one-time security validation
that the project cannot obtain otherwise.

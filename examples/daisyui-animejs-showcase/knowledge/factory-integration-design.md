# Capacité « maîtrise anime.js + daisyUI » dans le process Factory — design

> Conçu par Workflow ultracode (4 lecteurs ancrés code/docs réels + 2 architectes + synthèse adversariale). Proposition de design — rien n'est encore écrit dans Factory.

## Verdict

Les deux propositions sont en realite la MEME architecture (module de connaissance versionne hashe par provenance + prompt-kind d'authoring + lint CSP deterministe re-incarne de check-csp.mjs), divergant seulement par l'ampleur du scope livre d'un coup. La proposition « minimale » et la « deepest » convergent sur les memes seams testes et respectent toutes les prior_decisions sans en rouvrir aucune. Je recommande l'hybride-phase : livrer d'abord le noyau minimal qui prouve la valeur (promotion du pack anime.js + prompt-kind app-authoring), puis derouler gate CSP, daisyUI et copilote en phases additives. La forme « tout d'un coup » est un sprint Factory complet a risque de livraison partielle, contraire a la directive PO « chaque sprint livre TOUT son objectif » SI l'objectif est mal borne — donc on borne l'objectif au noyau prouve, et on sequence le reste comme phases d'un meme sprint Factory, pas comme defers.

**Recommandé : `hybride-phase`** — Les deux stances composent identiquement les prior_decisions : 1er geste = SKILL.md/prompt-kind gout SBFB 0-execution rollback-gratuit (factory_opencodesign:299/444), connaissance = couche prompt read-only jamais runtime tiers, copilote via ExecutionTarget::Ollama keyless jamais pi-ai, scellage 100% Factory non-delegable, maquette-first = gate PROCESSUS pas FGx, autorite descendante process>RRV>Factory, provider!=backend execution, PR-plugin OCD differee. La SEULE difference reelle est : faut-il livrer les 7 etages (kind+gate+daisyUI+template+copilote+self-check) en un bloc, ou commencer par le couple {promotion pack + prompt-kind} qui surface DEJA la maitrise a tout agent. L'utilite LLM est maximale et immediate au plus petit livrable : `process prompt --kind app-authoring` imprime synthesis distille + verdict CSP par-primitive + 9 pieges durs a TOUT provider, couple mecaniquement au disque par le test prompt_kinds_resolve_to_existing_files (process.rs:891-901) — pas de bump wire, pas de dep, 100% infra existante. Le reste (gate, daisyUI, copilote) augmente la garantie mais n'est pas prerequis pour que la connaissance soit consommee. Hybride = livrer la capacite-coeur prouvee, puis durcir, sans sur-ingenierie en avance de phase.

## Forme de la capacité

Une CAPACITE DE PROCESS, pas un runtime ni une vitrine : (1) un MODULE DE CONNAISSANCE VERSIONNE repo-visible (docs/factory/knowledge/animejs/ + plus tard /daisyui/), 5 couches + MANIFEST.json (version lib, date snapshot, hash), hashe+signe gratuitement par provenance::compute_output_hash tree-walk blake3 + FG8 des qu'il est dans le source ; (2) un PROMPT-KIND d'authoring (app-authoring/ui-knowledge) enregistre dans PROMPT_KINDS, fiche-passerelle CONDENSEE (synthesis distille + verdict CSP + pieges + pointeurs hash vers couches lourdes) servie par `sbfb-factory process prompt`, vendor-neutre claude/codex/gpt/local/human via depth+strip_cloud_references ; (3) un GATE CSP DETERMINISTE (re-incarnation Rust de check-csp.mjs, 100% regex/statique, FAIL=blocage) branche au pipeline publish a cote de FG5/FG6. Etage optionnel non-prioritaire : copilote Ollama qui prepend le bloc de capacite dans assemble_prompt, et starter template daisyui vendore same-origin. La substance = savoir injecte + contrat de conformite mecanique ; le copilote et le template sont des amplificateurs, jamais le coeur.

Sources : repo daisyUI v5 MIT + Tailwind v4 + daisyui.com/docs verbatim. Couches : (1) components.json/COMPONENTS.md = catalogue exhaustif composants (btn, card, modal, drawer, tabs, alert...) + modifiers (-primary, -outline, -lg) + responsive + etats, chacun annote verdict CSP ; (2) classes-bank.json = blocs HTML verbatim + sbfb_reusable{ok,why} ; (3) docs.json/DOCS.md officielle verbatim ; (4) theming.json = systeme oklch + variables (data-theme, --color-*, color-mix) comme substitut au .d.ts absent (daisyUI = CSS, pas de surface .d.ts) ; (5) synthesis.json = compositions composant+anime CSP-safe. VOIE BUILD TRANCHEE (prior_decision + reference vivante input.css/package.json vitrine) : daisyUI=plugin Tailwind compile BUILD-TIME (tailwindcss --minify, source(none)+@source explicite pour purger), produisant UN app.css vendore same-origin ; JAMAIS Tailwind-CDN (interdit memory), JAMAIS Google Fonts. MANIFEST.json daisyui = version v5 + Tailwind v4 + date + hash. C'est une phase M-L, pas le 1er livrable.

## Comment la connaissance est surfacée au LLM

Trois canaux, tous via l'infra existante, 0 nouvelle autorite. (1) PROMPT-KIND universel : au moment de fabriquer une app, l'agent fait (ou recoit) `sbfb-factory process prompt --kind app-authoring --provider {claude|gpt|local}` ; prompt_data (process.rs:796-835) lit prompts/agent/app-authoring.md, applique depth, strip_cloud_references pour local (meme connaissance, moins de profondeur). C'est le canal vendor-neutre garanti, couple mecaniquement au .md par le test prompt_kinds_resolve_to_existing_files (FAIL au build si kind ajoute sans fichier). (2) CONTEXT-PACK Operator : handle_context_pack (operator_server.rs:355-427) + handle_chat_session (:648-700) gagnent un champ authoring_knowledge {path, hash blake3 via file_hash} pointant docs/factory/knowledge/*/MANIFEST.json, donc une session fraiche recoit la matrice CSP-annotee verifiable-par-recalcul au meme rang que base/universal/handoff ; chat_history_authoritative=false preserve. (3) ROUTING AUTOMATIQUE : la Routing-table memory->zone des 2 SKILL.md (preflight + review) gagne une zone 'UI/animation/design app SBFB' pointant vers le module — comme la zone 'lib externe' pointe deja vers context7 — donc toute phase/app touchant le front surface AUTOMATIQUEMENT la contrainte CSP + la maitrise. (4) COPILOTE (etage engage, non-MVP) : assemble_prompt (llm_bridge.rs:61-93) prepend le bloc capacite UI avant le message, dispatch ExecutionTarget::Ollama keyless apres SENSITIVE_ACTIONS. USAGE concret : le LLM biaise le sampling par cross_products/novelty_levers, applique le filtre dur CSP par-primitive, evite les pieges codes, vendorise same-origin. Connaissance CONSOMMEE/AFFICHEE, jamais autoritaire ; aucun verdict PASS (artifact-draft anti-PASS preserve). UX Operator = intention lisible ('Donner a l'agent la maitrise UI/animation pour cette app'), pas le jargon kind/provider.

## Garde-fous CSP (enforced)

- LINT STATIQUE DETERMINISTE (gate, mecanique) : re-incarnation Rust de check-csp.mjs, branchee au pipeline publish a cote de FG5/FG6. Reprend la table NETWORK verbatim du CODE (check-csp.mjs:23-37) : remote <link href https>, remote <script src https>, @import url(), url() https, fetch(), XMLHttpRequest, WebSocket, EventSource, navigator.sendBeacon, new Worker, new SharedWorker, importScripts, navigator.serviceWorker. 3 tiers : authored (index.html/app.js) = 0 URL http(s) absolue + 0 network ; compiled (app.css) = 0 network + chaque URL absolue dans CSS_URL_ALLOW = {http://www.w3.org/2000/svg, http://www.w3.org/1999/xlink (namespaces dans data:, jamais fetched), https://tailwindcss.com (banner MIT)} ; vendored = 0 primitive reseau live. FAIL deterministe = publish bloque. Jamais un jugement LLM (contrainte FACTORY_GATES.md:205-207).
- ATTENTION DRIFT DOC : le commentaire check-csp.mjs:12 dit 'anime.esm.js' mais le check reel ligne 75 lit 'vendor/anime.umd.js'. Le CODE (UMD) est la verite ; le commentaire est perime. La re-incarnation Rust DOIT prendre le code comme source unique des regles, pas le commentaire — et idealement factoriser les regles en une source partagee pour eviter la divergence regex-JS-vitrine vs gate-Rust-Factory.
- VERDICT CSP PAR-PRIMITIVE (advisory, en amont) : le champ sbfb_csp.usable+reason de chaque primitive anime.js / classe daisyUI est dans le prompt-kind, donc le copilote ECARTE les candidats non-CSP-safe AVANT de generer. Double filet : advisory au prompt + mecanique au gate.
- PIEGES CSP DURS codes verbatim dans le prompt-kind : box-shadow JAMAIS animee (glow = box-shadow STATIQUE ::after, opacity-only, GPU-composite) ; SVG peint en var(--color-*)/color-mix(in oklch) car fill-*/stroke-* Tailwind ne compilent pas dans l'iframe ; createMotionPath element cx=0/cy=0 (translate s'ajoute a la geometrie) ; morphTo mono-trace meme type d'element ; prefers-reduced-motion non-gere-par-anime -> brancher etat-final (revert/seek(duration)/utils.set) + garde-fou CSS durations 0.001ms !important.
- DOCTRINE VENDORISATION same-origin : anime.js en UMD/global window.anime (script CLASSIQUE, JAMAIS <script type=module>/ESM car origine opaque + COEP require-corp interdisent le fetch CORS de ses propres assets) ; daisyUI/Tailwind compile build-time en app.css same-origin. Documente comme regle canonique dans le prompt-kind.
- SELF-CHECK runtime re-incarne SANS Electron (etage de durcissement, pas MVP) : rejeu de l'app dans le viewer iframe blob_serve sous la CSP REELLE de prod (connect-src 'none', origine opaque, COEP require-corp) via postMessage. Complement RUNTIME du lint STATIQUE, obligatoire pour les url()/@font-face construits a l'execution qui echappent au lint.
- SCELLAGE INTACT : la connaissance n'accorde AUCUNE dispense. CSP/COEP/COOP/FG5/FG6/FG8/Ed25519 restent souverains. Le lint authoring est ADDITIF ; FG6 lock==provenance reste vrai car tout asset vendore est hashe par compute_output_hash.
- A CONFIRMER cote daemon : la CSP exacte servie par blob-serve (nexus-shell-daemon BLOB_SERVE_CSP) doit etre verifiee egale a celle citee en commentaire check-csp.mjs AVANT d'en faire le contrat de gate — sinon le lint protege une CSP fictive.

## Annexe A — les 2 architectures

### Minimale et alignee. Le plus petit artefact qui s'insere dans le process-portable/Factory EXISTANT, ZERO nouvelle infra reseau, ZERO dependance nouvelle, mono-auteur. La capacite "maitrise anime.js + daisyUI" entre par les trois seams deja en place et deja testes : (1) un PROMPT_KIND d'authoring assemble par `sbfb-factory process prompt` (process.rs:7-16), (2) un module de connaissance versionne repo-visible hashe/signe GRATUITEMENT par provenance, et (3) un lint CSP DETERMINISTE re-incarne de check-csp.mjs en Rust, branche dans le pipeline publish a cote de FG5. Le 1er geste est un SKILL.md "gout SBFB" (0 execution, 0 merge coeur, rollback gratuit), exactement comme acte par l'etude OpenCoDesign. On NE re-debat AUCUNE prior_decision : connaissance = couche prompt/skill read-only, copilote = ExecutionTarget::Ollama keyless, scellage 100% Factory, CSP non-negociable, tokens per-app COPIE same-origin, maquette-first = gate processus. La nouveaute non-actee (anime.js/daisyUI specifiques) est seulement de l'INSTANCIATION de patterns deja figes, pas une nouvelle doctrine. — app-authoring : capacite UI CSP-safe (anime.js + daisyUI) pour le process Factory

- **Forme** : Trois couches qui REUTILISENT l'existant, aucune n'est un nouveau sous-systeme :

1. CONNAISSANCE VERSIONNEE (data, repo-visible) — un module promu hors de l'exemple vers `docs/factory/knowledge/animejs/` et `docs/factory/knowledge/daisyui/`, copie du layout 5-couches deja construit (primitives.json/synthesis.json/examples-bank.json/docs.json/types). ### factory-cli-process

Le crate `sbfb-factory` est un binaire CLI Rust (clap) avec deux familles de commandes : (1) le pipeline de fabrication d'app (`create`, `fork`, `redeploy`, `validate`, `preview`, `publish`, plus gates `diff`/`scan-secrets`/`sandbox`/`preview-check`) et (2) l'outillage de PROCESSUS agent (`process` et `operator`). `create` instancie un des 4 templates compiles-in (`static`, `static-reader`, `react`, `pyodide`) via include_str! + substitution `{{name}}`/`{{version}}`, en emettant SBFB.json v2, factory.template.lock et factory.provenance.json. `sbfb-factory process` fait l'observabilite (status-sprint, lint-planning, audit-commit, context) ET l'ASSEMBLAGE DE PROMPT/CONTEXT-PACK (`process prompt --kind --provider`, et `operator serve` route POST /api/context-pack). Point crucial pour l'intention PO : la "connaissance/guidance" assemblee aujourd'hui est exclusivement du PROCESSUS de sprint (preflight, review, commit-body, audit-gate) lue depuis `prompts/agent/*.md` ; il n'existe AUCUNE connaissance d'AUTHORING d'app (UI/anime.js/daisyUI) ni dans les prompts, ni dans le crate. La seule guidance d'authoring + la contrainte CSP du sandbox (`default-src 'self'; connect-src 'none'`, no-CDN, no-fetch) vit aujourd'hui inline dans les templates (commentaires HTML + README de chaque template). `operator serve` est un serveur JSON axum loopback auth-gate (Host+Origin+token) avec actions allowlistees, brouillons d'artefacts allowlistes (PASS interdit), chat/stream gate sur SENSITIVE_ACTIONS, et dispatch d'un agent via ExecutionTarget (claude/ollama/network).

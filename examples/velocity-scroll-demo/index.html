Velocity scroll

L'inclinaison de la pile suit la vitesse de défilement. Tout est en JavaScript vanilla (boucle requestAnimationFrame, style WAAPI), zéro dépendance, zéro CDN, zéro réseau — donc ça tourne tel quel sous la CSP du bac à sable SBFB (connect-src 'none').

Fais défiler vite, puis lentement — regarde le skew et le HUD.

technique

Vélocité = Δposition / Δtemps

Chaque frame, on lit window.scrollY, on calcule la vitesse signée (px/ms) et on la lisse avec un ressort minimal (lerp). Aucun écouteur de scroll, aucun throttle manuel.

CSS var

Le JS écrit, le CSS applique

Le JS pose --vel sur :root ; le CSS fait le rendu (transform: skewY(var(--vel))). Séparation propre, accéléré GPU.

souveraineté

0 CDN, 0 fetch

L'animation n'a pas besoin du réseau : connect-src 'none' ne la gêne pas. Une vraie app embarquerait ses polices en woff2 dans l'archive.

WAAPI

Même esprit que Motion One

Motion One ne fait que rendre la WAAPI agréable. Ici on reste en natif : la même logique (vélocité → spring → transform) en ~15 lignes, sans aucune lib.

a11y

prefers-reduced-motion respecté

Si l'utilisateur a réduit les animations, la pile reste droite et le bandeau s'arrête. C'est une exigence du design system SBFB (Reflect).

perf

On anime transform, pas le layout

Seul transform change (compositeur GPU), jamais width/top. Fluide même sur mobile.

design

Esthétique Reflect

Surfaces opaques neutres, accent near-white, mono pour les chiffres, hairlines. Les tokens sont copiés dans l'app — la couche per-app du DS à deux couches.

portable

Un seul fichier

index.html + SBFB.json. CSS et JS inline (autorisés par 'unsafe-inline'). Rien d'autre à charger.

✓ tourne sous la CSP réelle de production

Cette page démontre qu'on peut faire de belles animations dans une app SBFB sans framework et sans rien charger depuis internet. Le moteur natif (WAAPI / CSS) couvre l'essentiel ; pour aller plus loin on vendoriserait une petite lib (Motion One ~2–18 Ko, anime.js…) dans l'archive, jamais via CDN.

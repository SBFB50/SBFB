Architecture du réseau

SBFB est un réseau P2P décentralisé de compute et d'hébergement d'apps. Pas de serveur central, pas d'administrateur — uniquement le protocole.

Composants principaux

Shell Daemon
Processus singleton Rust qui gère la couche P2P (iroh 0.98), le discovery des pairs, le pipeline curator, et l'API HTTP loopback. Il orchestre tout sans jamais exposer de port réseau public.
Coordinator
Module intégré au daemon responsable du dispatch des tâches vers les workers, de la validation des résultats, de l'attribution des kudos, et du stockage applicatif. Base SQLite locale.
Workers
Noeuds de compute headless qui exécutent les tâches (LLM via Ollama, WASM, scripts). Chaque worker dispose d'une allowlist de tâches acceptées et d'un consentement GPU à 4 niveaux.
iroh P2P
Substrat réseau basé sur iroh 0.98 : gossip pour la propagation en temps réel, blobs pour le transfert de données volumineuses, docs pour le stockage répliqué. Fonctionne en LAN et WAN sans configuration.

Cycle de vie d'une app

N'importe qui publie une app sur le réseau. Le processus est entièrement vérifiable : du code source au zip déployé, chaque étape est traçable.

  1. Code source

    L'app vit dans un dépôt Git public. Toute techno qui produit du HTML est supportée : React, Vue, Python/Pyodide, WASM, Jupyter, HTML pur.

  2. Verified deploy

    Le coordinator clone le dépôt, vérifie la signature Ed25519 du développeur via Keyoxide, construit l'archive, et génère un fichier provenance.json SLSA L1. Le code sur le réseau = le code du dépôt.

  3. Archive zip

    L'app est empaquetée en une archive zip contenant un index.html et ses ressources. Format universel, aucune dépendance à un framework ou runtime spécifique.

  4. Distribution P2P

    L'archive est distribuée via iroh-blobs. Chaque noeud qui la télécharge peut la re-servir aux autres pairs.

  5. Rendu en iframe

    Le daemon Rust blob-serve décompresse le zip, cache les fichiers en LRU mémoire, et les sert dans un iframe sandboxé (sandbox="allow-scripts" sans allow-same-origin, CSP connect-src 'none').

Cycle de vie d'une tâche

Le réseau SBFB permet aux apps d'envoyer des tâches de compute (inférence LLM, traitement de données, etc.) aux workers du réseau. Voici le cycle complet.

  1. Soumission

    L'app dans l'iframe appelle bridge.submitTask({prompt, task_type}). Le message traverse le bridge postMessage vers le shell host, qui le forward au coordinator.

  2. Dispatch

    Le coordinator évalue les workers disponibles selon leur allowlist, leur capacité GPU, et leur charge actuelle. La tâche est envoyée au worker le plus adapté via le protocole P2P.

  3. Exécution

    Le worker exécute la tâche dans son runtime (Ollama pour LLM, WASM pour compute pur). Le résultat est renvoyé au coordinator avec les métriques d'exécution.

  4. Validation

    Le coordinator valide le résultat : conformité au format attendu, filtrage PII (GLiNER + regex), vérification d'intégrité. Les résultats invalides sont rejetés.

  5. Kudos

    Si le résultat est valide, le worker reçoit des kudos — un score de réputation non-monétaire, non-transférable, lié au projet. Les kudos reflètent la contribution sans jamais devenir une monnaie.

Modèle de sécurité

La sécurité de SBFB repose sur plusieurs couches de défense en profondeur. Aucune couche n'est suffisante seule — c'est leur combinaison qui protège le réseau.

Loopback HTTP durci

L'API HTTP du daemon n'est accessible que via loopback (127.0.0.1). Chaque requête est vérifiée : token bearer, headers Host et Origin, et credentials du processus pair (UDS/Named Pipes sur Windows).

Sandbox iframe

Les apps tournent dans un iframe avec sandbox="allow-scripts" — pas de allow-same-origin, donc aucun accès aux cookies, au localStorage, ou aux APIs du domaine parent. CSP connect-src 'none' bloque les requêtes réseau directes.

Curators Ed25519

Les listes d'apps sont maintenues par des curators qui signent avec leur clé Ed25519. Pas de modération centrale : chaque utilisateur choisit les curators qu'il suit. Les listes sont propagées via gossip et vérifiées cryptographiquement.

Résistance Sybil

Le système d'invitations et de kudos per-project empêche la création massive de fausses identités. Un noeud sans historique de contribution vérifié ne peut pas influencer le réseau.

Deploy vérifié

Chaque app publique est déployée depuis son code source via Keyoxide + provenance SLSA L1. Il est impossible de déployer un binaire qui ne correspond pas au code du dépôt.

Protection PII

Le bridge offre piiRedact() : filtrage des données personnelles (GLiNER ONNX + regex) avant qu'elles n'atteignent les workers. Défense en profondeur côté transport et côté output.

Vérification & Provenance

Chaque app publique SBFB est déployée depuis son code source via un processus vérifiable. Le coordinator clone le dépôt, vérifie la signature Ed25519 du développeur via Keyoxide, construit l'archive zip, et génère un enregistrement de provenance SLSA L1 signé. Le résultat est un provenance.json intégré à l'archive, dont le hash BLAKE3 est propagé dans l'annonce réseau.

Chaîne de preuve

Dépôt Git ──▶ Clone ──▶ Keyoxide Ed25519 ──▶ Build zip ──▶ provenance.json
                                                    │
                                            BLAKE3 hash ──▶ Annonce réseau
                                                    │
                                            Signature Ed25519 ──▶ Vérification

Champs de provenance

repo_url
URL du dépôt source Git d'où l'app a été clonée.
commit_sha
Hash du commit exact utilisé pour construire l'archive.
artifact_hash
Hash BLAKE3 de l'archive zip produite.
signature
Signature Ed25519 de l'enregistrement de provenance par le noeud coordinator.
node_id
Identifiant du noeud coordinator qui a effectué le deploy vérifié.
timestamp
Date et heure du deploy.
schema_version
Version du format de provenance (actuellement 1).

Vérification interactive

Sélectionnez un projet et vérifiez sa provenance en temps réel. La vérification appelle le daemon local qui valide la signature Ed25519 de l'enregistrement de provenance.

Philosophie

Zéro administration

Pas de compte à créer, pas de serveur à configurer. Lancez le daemon, rejoignez le réseau, publiez une app. Le protocole gère tout : discovery, distribution, validation.

Open source par construction

Chaque app publique est déployée depuis un dépôt Git vérifié. Les utilisateurs peuvent en un clic voir le code source, signaler un bug, proposer une feature, contribuer via PR, ou forker l'app et déployer leur propre version. Le modèle F-Droid/Linux appliqué aux apps web P2P.

Pas de monnaie

Les kudos sont un score de réputation, pas une monnaie. Pas de dépôt, pas de mise, pas de transfert, pas de brûlage. La contribution est reconnue, jamais monétisée.

Décentralisation réelle

Pas de noeud bootstrap privilégié, pas de fondation, pas de gouvernance centralisée. Le modèle OpenBSD : un maintainer, un protocole documenté, une communauté qui contribue librement.

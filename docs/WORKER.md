# nexus-worker

`nexus-worker` is the single-binary GPU contributor for the
nexus-grid / SBFB peer-to-peer compute network. It runs on a
volunteer's machine, connects to the projects they have
explicitly opted into, and serves LLM inference tasks to the
coordinator of each project through the local Ollama backend.

This document describes **Sprint 3** functionality: install,
register an identity, join a project via an invite token, run
the worker headless or with a terminal dashboard, and inspect
local state.

## Install

### Pre-built binary

Download the right binary for your platform from the GitHub
release page and put it on your `$PATH`:

| Target | File |
|---|---|
| Linux x86_64 (glibc) | `nexus-worker-x86_64-unknown-linux-gnu` |
| Linux x86_64 (musl, static) | `nexus-worker-x86_64-unknown-linux-musl` |
| Linux aarch64 (glibc) | `nexus-worker-aarch64-unknown-linux-gnu` |
| Linux aarch64 (musl, static) | `nexus-worker-aarch64-unknown-linux-musl` |
| Windows x86_64 | `nexus-worker-x86_64-pc-windows-msvc.exe` |
| macOS Intel | `nexus-worker-x86_64-apple-darwin` |
| macOS Apple Silicon | `nexus-worker-aarch64-apple-darwin` |

All targets are cross-compiled by
[`.github/workflows/build-worker.yml`](../.github/workflows/build-worker.yml)
on every push to `master` and every tag starting with `v`.
musl variants are fully static; glibc variants need the libc
shipped with the distribution.

### Ollama prerequisite

`nexus-worker` expects a running Ollama daemon on the same
machine. Install it from <https://ollama.com/download> and
start the service (`ollama serve` on Linux, automatic on
Windows/macOS). The worker will continue running if Ollama is
not reachable, but it will stay in the `CONNECTING` state
until the daemon comes up.

### Build from source

```bash
git clone https://github.com/FlowUP/nexus
cd nexus
cargo build --release -p nexus-worker
./target/release/nexus-worker --version
```

Rust 1.78+ is required. No system libraries; SQLite is bundled
and NVML loads via `libloading` at runtime.

## Quick start

```bash
# 1. Create a persistent identity + config (one-time)
nexus-worker register --name "rtx5080-home"

# 2. Accept an invite from a project coordinator
nexus-worker join nx1AAAA...

# 3. Run the engine (headless)
nexus-worker start

# Or with the ratatui dashboard
nexus-worker start --tui
```

## Filesystem layout

All worker state lives in one platform-specific directory:

| OS | Directory |
|---|---|
| Linux | `~/.config/nexus-grid/` and `~/.local/share/nexus-grid/` |
| macOS | `~/Library/Application Support/dev.FlowUP.nexus-grid/` |
| Windows | `%APPDATA%\FlowUP\nexus-grid\` |

Inside that directory:

```
worker.toml            configuration (human-editable)
data/worker.key        Ed25519 secret key (0600 on Unix)
data/allowlist.sqlite3 enrolled projects + daily budgets
logs/worker.log        rotating daily JSON logs
cache/                 model / blob cache (reserved)
```

Pass `--config <PATH>` on any subcommand to point at a
non-default `worker.toml`. Every other directory is derived
from the config file's parent so fixtures for tests and
multi-identity setups work with a single flag.

## Configuration (`worker.toml`)

Generated by `nexus-worker register`. Every value is optional
at load time; omitted fields fall back to the defaults below.

```toml
[identity]
# Human-readable name, stored locally, never shared.
name = "rtx5080-home"

[ollama]
# Ollama HTTP endpoint. Default matches the `ollama serve`
# install.
endpoint = "http://localhost:11434"
# Per-request timeout in seconds.
timeout_secs = 300

[gpu]
# Fraction of total VRAM the worker may consume, clamped to
# [0.1, 1.0] on load.
max_vram_fraction = 0.9

[engine]
# Poll interval in milliseconds, minimum 100.
task_poll_interval_ms = 2000
# Max concurrent tasks, minimum 1.
max_concurrent_tasks = 1

[logging]
# tracing-subscriber EnvFilter directive.
level = "info"
```

### Environment variable overrides

Every field can also be overridden via an environment variable
with the `NEXUS_WORKER__<SECTION>__<KEY>` naming convention
(double underscores for section separators):

```bash
NEXUS_WORKER__OLLAMA__ENDPOINT=http://10.0.0.5:11434 \
    nexus-worker start
```

Precedence (highest wins): env vars > `worker.toml` > built-in
defaults.

## Subcommands

### `register [--name NAME]`

First-time bootstrap. Creates the data directory, generates a
fresh Ed25519 keypair at `data/worker.key`, writes
`worker.toml`, and prints the public key in hex so you can
share it with a project coordinator for out-of-band
authorization.

Refuses to clobber an existing registration — delete
`worker.toml` manually if you really want to rotate the
identity (note that this loses any kudos tied to the old
pubkey).

### `join <INVITE>`

Accepts a signed invite token from a project coordinator.
The token is a single `nx1...` base32 string that encodes:

- project namespace id
- project name
- coordinator Ed25519 public key
- optional coordinator endpoint hint (relay / direct addrs)
- scope (worker or observer)
- expiry

The worker decodes the token, verifies the signature against
the embedded pubkey, rejects it if expired, and appends the
project to the local allowlist with `enabled = true` and an
unlimited default budget.

Re-pasting an already-accepted invite is a friendly no-op, so
`join` is idempotent from the user's perspective.

### `projects list | enable | disable | budget`

Manage the allowlist.

```bash
# Show every enrolled project
nexus-worker projects list

# Pause / resume claim acceptance for a project
nexus-worker projects disable proj-abc
nexus-worker projects enable  proj-abc

# Set a daily energy budget (joules). 0 = unlimited.
nexus-worker projects budget proj-abc 1800000
nexus-worker projects budget proj-abc 0
```

The engine uses `list_enabled()` on each tick to decide which
projects are claim-able. Disabled projects keep their stats
but do not receive any new work.

### `start [--tui | --headless]`

Boot the engine. Without a flag, the worker runs headless and
prints state transitions to stdout. With `--tui`, it launches
the ratatui dashboard in the alternate screen buffer.

Ctrl+C triggers a graceful shutdown in both modes: the state
machine transitions to `Shutdown`, the iroh node closes via
`Router::shutdown().await` (the Sprint 2 audit-fixed graceful
path), and any open SQLite connections flush to disk.

**TUI keys**:

| Key | Action |
|---|---|
| `q` / `Q` / `Esc` | Shutdown engine and exit |
| `↑` / `↓` | Scroll the projects list |
| `PgUp` / `PgDn` | Fast scroll by 10 |

### `stats`

Print a machine-readable snapshot of the worker state:
identity, allowlist path, ollama endpoint, and a marker
telling you whether the W4 (GPU) + W6 (state) + W7
(allowlist) backends are live.

### `config get <KEY>` / `config set <KEY> <VALUE>`

Read or update a single configuration key. The full set of
keys is documented above under
[Configuration (`worker.toml`)](#configuration-workertoml).
Sprint 3 ships these as stubs pointing at W3; they go live in
a follow-up once the interactive `set` path lands.

### `browse`

Placeholder for the DHT browsing flow: once the curator list
wrapping lands in W9.1 / Sprint 4, this subcommand will query
the iroh pkarr DHT, filter through the configured curator
list, and render a selectable list of public projects.

## Engine states

The worker is a simple finite state machine. States you can
observe in the `start` output or the TUI:

| State | Meaning |
|---|---|
| `idle` | Registered, no network activity yet |
| `connecting` | Reaching a coordinator and waiting for preconditions (Ollama reachable, at least one enabled project) |
| `pulling_model(name, %)` | Downloading a model via Ollama |
| `processing(n active)` | Ollama ready, projects enrolled, claiming and running tasks |
| `paused` | User paused (Ctrl-P-style; drains in-flight work) |
| `error(reason)` | Unrecoverable failure; awaits manual `clear` |
| `shutdown` | Terminal — the process is exiting |

Legal transitions are exhaustively tested in
`crates/nexus-worker-core/src/engine/state.rs::tests`.

## Logs

Every event emitted by `nexus-worker-core` is routed to two
sinks:

- **stdout**: human readable, ANSI coloured only on a TTY.
  Filter from `$RUST_LOG`, the CLI `-v` / `-vv` / `-vvv`
  counter, or the `[logging] level` config.
- **`logs/worker-YYYY-MM-DD.log`**: JSON, one record per
  line, rotated daily via
  [`tracing-appender`](https://docs.rs/tracing-appender).
  Fixed at `info+` regardless of `-v` so verbose interactive
  sessions don't blow up the on-disk log.

## GPU backends

Sprint 3 ships two backends for `GpuMonitor`:

- **nvml** (NVIDIA): dynamically loads `libnvidia-ml.so` /
  `nvml.dll` at runtime via `libloading`. No compile-time
  dependency on CUDA / NVIDIA — the binary still runs on
  machines without a driver, falling back to Noop.
- **noop**: always present, reports zero devices. Selected
  automatically when NVML init fails. The engine continues
  in CPU-only mode.

AMD ROCm and Apple Metal backends are planned for v1.1; the
trait is designed so they plug in without touching the
engine loop.

## Troubleshooting

**"worker not registered" on `start` or `join`**
: You skipped `nexus-worker register`, or `--config` points at
  a path that does not yet exist. Run `register` first.

**"already registered" on `register`**
: A `worker.toml` already exists. Delete it manually if you
  really want a fresh identity.

**"ollama not running" warning in the logs**
: The engine cannot reach Ollama at the configured endpoint.
  Check that `ollama serve` is running (`curl http://localhost:11434/api/tags`),
  then the worker will transition into `processing` on the
  next tick (default 2s).

**"invite token is expired"**
: The token's `expires_at_unix` is in the past. Ask the
  coordinator for a fresh one.

**Base32 decoding failed**
: The invite was truncated or mangled in transit. Copy the
  full `nx1...` string, making sure nothing else got included.

## What's not in Sprint 3

- **Actual task claim / execute / result write-back**: the
  engine loop has the hooks (see the `TODO(W9.1)` markers in
  `crates/nexus-worker-core/src/engine/runtime.rs::tick`) but
  the full flow requires the Sprint 4 coordinator shipping
  `task:*` entries into a project doc, and the invite format
  gaining a `DocTicket` field so the worker can import and
  sync the doc.
- **Curator list browsing**: `browse` is a placeholder.
- **Live GPU stats in the TUI body**: the engine probes GPUs
  at boot but does not broadcast per-tick snapshots yet. W9.1
  will add a `tokio::sync::watch<Vec<GpuStats>>` channel.
- **Pause / resume from the CLI**: the state machine has the
  events (`Pause`, `Resume`) but there is no subcommand to
  trigger them yet.

All of the above are tracked in the SBFB plan
`magical-marinating-phoenix.md` and arrive in the Sprint 3
W9.1 follow-up + Sprint 4.
